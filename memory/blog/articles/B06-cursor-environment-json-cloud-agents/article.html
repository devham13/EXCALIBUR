Cloud Agent в Cursor работает не на вашем ноутбуке, а на отдельной Ubuntu-машине с клоном репозитория. Без файла `.cursor/environment.json` каждый запуск превращается в лотерею: то нет Node, то не поднялась база, то команда живёт только в личном wizard dashboard. Настройка cursor cloud agent через config-as-code занимает около часа. Ниже вы закрепите окружение в Git, дождётесь зелёного Build, разделите команды install и start и проверите тестовый агент на feature branch.

TL;DR / Быстрый инсайт: `.cursor/environment.json` – это "рецепт" виртуальной машины для облачного агента в репозитории. Команда install выполняется при Build и попадает в snapshot диска; start и terminals – при каждом run агента. Приоритет конфига: файл в репо выше personal и team wizard. Build failed не ломает команду: агенты стартуют с последнего успешного active Build.

Hosted Cloud Agent работает на изолированной Ubuntu VM с clone репо, secrets и сетью. Файл cursor environment json задаёт snapshot или Dockerfile, install и команды run. Build "замораживает" диск с зависимостями; без active Build агент опирается на прошлый snapshot.

1. Сравните Cloud Agent и локальный Agent: когда нужен environment.json

Локальный Agent – для быстрых правок на ПК. Cloud Agent – для длинных задач, write-доступа к GitHub, фонового run и Automations. Окружение фиксируйте в репо, а не только в dashboard.

Сценарий Локальный Agent Hosted Cloud Agent + environment.json
Один раз поправить файл Достаточно IDE Избыточно
PR с тестами на CI-стеке команды Зависит от вашего ПК Репо-конфиг + Build
Automations / cron на репо Не работает без вашего ПК Обязателен стабильный Build
Self-Hosted Machines Свой сервер Файл environment.json не читается – только repos окружения

Делайте: коммитьте `.cursor/environment.json`, если Cloud Agents hosted – часть workflow. Не делайте: полагаться только на agent-led wizard без commit – личные настройки не попадут в PR коллегам.

2. Разберите структуру environment.json и приоритет над dashboard

Порядок: (1) `.cursor/environment.json` в репо, (2) personal saved, (3) team saved. Схема: environment.schema.json; лишние ключи reject, вместо `startup` – поле `start`. База: `snapshot`, `build.dockerfile` или `image`; snapshot важнее build. Пути dockerfile/context – от `.cursor/`, `..` = корень репо.

Пример минимального environment.json:
{ "snapshot": "YOUR_SNAPSHOT_ID", "install": "npm ci", "start": "sudo service docker start", "terminals": [ { "name": "web", "command": "npm run dev" } ], "ports": [ { "name": "app", "port": 3000 } ] }

Замените `npm ci` на свой менеджер пакетов (pnpm, pip, poetry). Делайте: храните минимальный JSON в Git и расширяйте по мере нужды. Не делайте: класть API-ключи в JSON – secrets только через dashboard.

3. Настройте Dockerfile и install: что готовить в Build

Build: Trigger → clone → install из корня → snapshot → active. install идемпотентен и повторяется на каждом Build; в snapshot только диск, не процессы и не shell export.

Workflow первого окружения:
GitHub read/write → guided setup или ручной `.cursor/` → install + опционально Dockerfile → commit → Builds tab → Trigger build → Success + active → test agent
  1. Шаг 1: Подключите репозиторий к Cursor Cloud Agents (GitHub с правами на clone и push).
  2. Шаг 2: Agent-led setup в dashboard (до 10 минут по docs) или папка `.cursor/` вручную.
  3. Шаг 3: Выберите базу: snapshot id из dashboard после Save или `build.dockerfile` с `context: ".."` для system deps из корня.
  4. Шаг 4: В Dockerfile не копируйте весь проект – checkout commit делает Cursor; COPY только для системных зависимостей.
  5. Шаг 5: Пропишите `install` под ваш lockfile (`npm ci`, `pnpm install --frozen-lockfile`, `pip install -r requirements.txt`).
  6. Шаг 6: Commit и push; при изменении config сработает триггер Configuration change или нажмите Manual trigger в Builds tab.
  7. Шаг 7: Дождитесь статуса Success и метки active Build перед production-задачами.

Делайте: короткий install. Не делайте: dev-сервер в install – только start/terminals.

4. Разделите start, terminals и ports: что запускать на каждый run

После boot: checkout ветки (код с branch, deps с Build), затем `start` и `terminals` на каждый run. start – коротко (Docker service); terminals – tmux с dev server; ports – подсказка агенту по портам.

Поле Когда выполняется Пример использования
install Каждый Build, из корня репо Установка npm/pip зависимостей в snapshot
start Каждый run агента Старт Docker, миграции БД одной командой
terminals Каждый run агента (tmux) `npm run dev`, queue worker
ports Документация для агента 3000 для фронта, 5432 для локальной БД

Делайте: проверяйте логи run, если агент "не видит" API на localhost – часто не поднялся terminal. Не делайте: дублировать тяжёлый install в start – Build уже должен был положить node_modules на диск.

5. Проверьте Builds: триггеры, логи и failed vs active

Триггеры Build: Recurring, Configuration change, Manual, Agent-requested. Recurring Skipped без новых commit/config на default. Failed Build: агенты на last good active Build. User secrets только при run, не в Build; stale builds по умолчанию 24h (`0` = всегда fresh default).

  1. Шаг 1: Откройте Environments → Builds tab после push environment.json.
  2. Шаг 2: Trigger build вручную или дождитесь configuration change.
  3. Шаг 3: При Failed откройте логи install/Dockerfile – исправьте и пересоберите.
  4. Шаг 4: Убедитесь, что active Build соответствует ожидаемому snapshot id.
  5. Шаг 5: Запустите test Cloud Agent с узкой задачей (lint или unit test).

Делайте: тест на feature branch. Не делайте: игнорировать логи failed Build.

6. Ограничьте secrets, egress и MCP в облаке

Secrets – в dashboard: build secrets для install, user secrets при boot. Поля `egressAllowlist`, `mcpServerAllowlist`, `disableAllMcpServers` ограничивают сеть и MCP в облаке. Локальный MCP – mcp.json; связка с Cloud – в гайде MCP для Cursor. Делайте: явный allowlist. Не делайте: секреты в JSON.

7. Пройдите чек-лист перед первым production run

  • GitHub подключён с нужными правами на репозиторий
  • `.cursor/environment.json` в репо, валиден по schema
  • install идемпотентен
  • Dockerfile без COPY всего workspace
  • start и terminals поднимают Docker/БД/dev server при run
  • Secrets только в dashboard, не в JSON
  • Build Success и active после merge или trigger
  • Логи failed Build просмотрены, если были ошибки
  • Test agent на feature branch выполнил lint/test
  • egress и MCP allowlist согласованы с безопасностью
  • stale builds threshold понятен команде (24h или 0)
  • Automations только после verify Build

environment.json не deprecated; snapshot id – в dashboard после Save.

8. Что делать дальше

  1. Зафиксируйте минимальный environment.json и дождитесь active Build.
  2. Разделите install и start/terminals по таблице выше и пересоберите Build.
  3. Запустите test agent с задачей "прогони тесты" на feature branch.
  4. Сверьте MCP allowlist с инструкцией по MCP и политикой команды.
  5. Для связки облачных агентов с бизнес-автоматизацией – модуль про Cursor и Make на курсе Make.com и вайбкодинга.

Частые вопросы

Чем install отличается от start в cursor environment?

install выполняется на этапе Build из корня репозитория и попадает в snapshot диска. start и terminals выполняются при каждом старте агента и поднимают процессы (Docker, dev server). Перенесите тяжёлые зависимости в install, а сервисы – в start/terminals.

Нужен ли Dockerfile для cloud agent?

Нет. Достаточно snapshot после agent-led wizard плюс install, или только install на базовом образе. Dockerfile нужен для системных пакетов, которых нет в snapshot; не копируйте весь проект в образ.

Как закрепить snapshot в environment json?

Сохраните окружение в Cloud Agents dashboard, скопируйте snapshot id, вставьте в поле `snapshot` в `.cursor/environment.json`, commit и push. Trigger build или дождитесь configuration change, проверьте active Build.

Почему агент не видит зависимости после build?

install упал или не идемпотентен – откройте логи failed Build. Агент на ветке с другим lockfile может потребовать обновить install. Убедитесь, что active Build успешен, а не только последний commit красный.

Deprecated ли environment.json?

Нет. Конфиг в репозитории имеет приоритет над personal и team wizard. Для Self-Hosted Machines файл не применяется – используйте настройки hosted Cloud Agents.

Где хранить user secrets и build secrets?

В dashboard Cloud Agents (Secrets / runtime). User secrets доступны при старте агента, не во время Build. Build secrets используйте для install, не коммитьте значения в Git.

Как протестировать cloud agent builds настройка без риска для main?

Push config на feature branch, trigger build, запустите agent from branch с узкой задачей. Hosted агент boot с active Build, затем checkout вашей ветки; исправляйте install по логам до Success.
