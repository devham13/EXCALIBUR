Agent в Cursor каждый раз "забывает", что вы отвечаете на русском, не трогает прод без спроса и работает в вашем стеке? Cursor Rules – постоянные инструкции для Agent (чат-ассистента в редакторе), которые подставляются в каждый запрос. За 30–45 минут вы создадите папку .cursor/rules/, два .mdc-файла (общий overview и правило под тип файлов), проверите Active Rules и закоммитите набор в git – без копипаста одних и тех же требований в каждый prompt.

TL;DR / Быстрый инсайт: Project Rules хранятся в .cursor/rules/ как файлы .mdc (markdown + YAML-шапка). Один файл с alwaysApply: true задаёт общие правила проекта; остальные включаются по globs, description или вручную через @-mention. Legacy-файл .cursorrules в корне устарел – переименуйте в backup и мигрируйте. Rules работают только в Agent, не в Tab. Проверка: Customize → Rules и вопрос в новом Agent-чате "какие правила активны?".

Rules – "стикеры на мониторе" для Agent: язык, запреты, стек. LLM (большая языковая модель) не помнит прошлые сессии – rules дают постоянный контекст. По Яндекс Вордстат (июнь 2026): "cursor rules" – ~248 показов/мес, "как настроить cursor" – ~186. Канон – документация Cursor Rules, актуально 15.08.2026.

Rules – "как думать в проекте". Внешние сервисы – через MCP: гайд по MCP в Cursor. Rules = поведение, MCP = доступ к API и браузеру.

1. Сравните Cursor Rules и legacy .cursorrules

Раньше .cursorrules в корне читался целиком в каждый запрос. С ~v0.43 (конец 2024) рекомендуют Project Rules: каталог .cursor/rules/ с .mdc и режимами активации. Legacy-файл ещё читается, но deprecated – два формата дают конфликтующие инструкции.

Критерий .cursorrules (legacy) .cursor/rules/*.mdc
Формат Один текстовый файл в корне Несколько .mdc с YAML frontmatter
Режимы Всегда целиком в контексте Always / по файлам / умно / вручную
Git и команда Один монолит Модули: overview + правила под HTML, Python и т.д.
Статус в 2026 Deprecated, но ещё читается Рекомендуемый способ (официальная docs)

Делайте: если в корне есть .cursorrules – переименуйте в .cursorrules.bak, перенесите смысл в 00-project-overview.mdc с alwaysApply: true. Не делайте: оставлять legacy-файл рядом с .mdc – Agent получит противоречивые указания и "забудет" часть правил.

2. Создайте папку .cursor/rules/ и первый .mdc

Project Rules версионируются в git. Нужна папка .cursor/rules/, не файл rules. Plain .md без YAML rules-система игнорирует – только .mdc с frontmatter между ---.

Workflow настройки:
Backup .cursorrules → создать .cursor/rules/ → добавить 00-project-overview.mdc → добавить stack-scoped .mdc → Customize → Rules → новый Agent-чат → тестовый prompt → git commit
  1. Шаг 1: Откройте проект в Cursor. Если есть .cursorrules – переименуйте в .cursorrules.bak.
  2. Шаг 2: В корне репозитория создайте каталог .cursor/rules/ (через проводник или терминал: mkdir -p .cursor/rules).
  3. Шаг 3: Создайте файл 00-project-overview.mdc – префикс 00 помогает держать overview первым в списке.
  4. Шаг 4: Вставьте YAML frontmatter и 3–15 коротких пунктов правил (см. следующий раздел).
  5. Шаг 5: Сохраните файл. Альтернатива: в Agent-чате команда /create-rule или Customize → Rules → Add Rule.

Docs: правило короче 500 строк. Делайте: короткие императивы. Не делайте: alwaysApply на 400 строк с GitHub – сожмите до 20–40 строк.

3. Выберите режим: alwaysApply, globs, description, @-mention

В интерфейсе Cursor (Customize → Rules) четыре типа. В YAML они задаются полями alwaysApply, globs и description. При alwaysApply: true поля globs и description игнорируются – не смешивайте "всегда" с привязкой к файлам в одном файле.

Режим в UI Frontmatter Когда использовать
Always Apply alwaysApply: true Язык, тон, запреты, стек – 1–2 коротких файла
Apply to Specific Files alwaysApply: false + globs Правила для HTML, Python, Make-сценариев и т.д.
Apply Intelligently description (без alwaysApply) Agent сам решает по описанию, когда правило уместно
Apply Manually без alwaysApply и без globs Подключение через @-mention имени правила в чате

Несколько globs – через запятую: **/*.html,**/*.css. User Rules только в Agent, не в Tab/Cmd+K. Приоритет: Team → Project → User. Делайте: логику проекта в git. Не делайте: дубли в User и Project Rules.

4. Настройте project-overview.mdc и правило под ваш стек

Минимальный рабочий набор – два файла: общий overview и одно file-scoped правило. Пример overview для автоматизатора или маркетолога с лендингами и скриптами:

Пример 00-project-overview.mdc:
---
description: Общие правила проекта
alwaysApply: true
---

- Отвечай на русском, простым языком без жаргона.
- Перед удалением файлов или деплоем – спроси подтверждение.
- Стек: HTML/CSS, Make-сценарии, Python для утилит.
- Коммиты: короткое сообщение на русском или английском, без "fix".
- Не выдумывай API-ключи и цены – если данных нет, скажи об этом.

Второй файл – под конкретный тип файлов. Пример для HTML-шаблонов:

Пример stack-scoped .mdc (HTML):
---
description: Правила для HTML-страниц и лендингов
alwaysApply: false
globs: **/*.html,**/*.htm
---

- Семантическая разметка: один h1, дальше h2/h3.
- Без inline style="..." – стили в отдельном CSS.
- Alt у каждого img, ссылки с понятным текстом.
- CTA-кнопки – контрастные, текст действия глаголом.

Шаблоны: cursor.directory, awesome-cursorrules – сократите под свой кейс. AGENTS.md – без YAML; .mdc – когда нужны globs. Делайте: 3–15 пунктов. Не делайте: абстракции вроде "будь полезным".

5. Проверьте Active Rules и устраните типичные сбои

Customize → Rules: overview – Always Apply, HTML-файл – Apply to Specific Files. Названия Auto Attached / Agent Requested в 2026 устарели.

  1. Шаг 1: Откройте новый Agent-чат (старый мог закешировать контекст без rules).
  2. Шаг 2: Спросите: "Какие project rules сейчас активны? Перечисли названия файлов."
  3. Шаг 3: Убедитесь, что 00-project-overview.mdc в списке Active Rules.
  4. Шаг 4: Откройте файл под glob (например index.html) и повторите вопрос – должно подтянуться stack-правило.
  5. Шаг 5: Дайте тестовый prompt без копипаста правил: "Добавь секцию hero на лендинг" или "Напиши функцию парсинга CSV". Сверьте diff с вашими пунктами.

Troubleshooting – правило "молчит":

  • Расширение .mdc, не .md – plain .md в .cursor/rules/ не подхватывается.
  • Закрывающая строка --- в frontmatter – без неё YAML битый.
  • Папка .cursor/rules/, не файл rules и не .cursor/rules.md.
  • Globs: запятая без пробелов между паттернами; проверьте путь **/*.html для вложенных папок.
  • Конфликт с .cursorrules – удалите legacy, если мигрировали.
  • Tab rules не использует – тест только в Agent.

Делайте: новый Agent-чат после правок. Не делайте: проверять через Tab.

6. Пройдите чеклист из 15 пунктов перед git commit

  • Legacy .cursorrules переименован или удалён, дубликатов нет
  • Каталог .cursor/rules/ – папка в корне репозитория
  • Есть 00-project-overview.mdc с alwaysApply: true
  • В overview 3–15 конкретных пунктов, без воды
  • Есть минимум одно file-scoped правило с globs под ваш стек
  • Каждый .mdc короче 500 строк (рекомендация docs)
  • Frontmatter валиден: открывающий и закрывающий ---
  • Расширение файлов .mdc, не .md
  • Customize → Rules показывает ожидаемые типы (Always / Specific Files)
  • Новый Agent-чат видит overview в Active Rules
  • Открытый файл под glob активирует второе правило
  • Тестовый prompt выполнен без копипаста инструкций в чат
  • User Rules не дублируют Project Rules
  • .cursor/rules/ добавлен в git (git add .cursor/rules/)

Import Remote Rule с GitHub → .cursor/rules/imported/ – сократите после импорта. Team Rules – планы Team/Enterprise; solo хватит Project Rules.

Частые вопросы

Как настроить cursor rules с нуля?

Создайте папку .cursor/rules/ в корне проекта. Добавьте файл .mdc с YAML frontmatter (alwaysApply: true для общих правил). Откройте Customize → Rules, проверьте тип правила. В новом Agent-чате спросите "какие правила активны?" и выполните тестовый prompt без копипаста инструкций.

Чем cursor rules отличается от .cursorrules?

.cursorrules – один устаревающий файл в корне, всегда целиком в контексте. Project Rules – набор .mdc в .cursor/rules/ с режимами Always, globs, description и ручным @-mention. Мигрируйте: backup старого файла, перенесите пункты в 00-project-overview.mdc.

Почему правило не применяется в Cursor?

Проверьте расширение .mdc, валидный YAML с ---, что .cursor/rules/ – каталог, а не файл. Сверьте globs (паттерны через запятую). Уберите конфликтующий .cursorrules. Тестируйте в Agent, не в Tab. Откройте новый чат после правок.

Сколько cursor rules можно добавить?

Формально – много файлов. На практике держите 1–2 коротких Always Apply и отдельные globs по типам файлов – каждый alwaysApply съедает контекст каждого запроса. Дробите большие правила; docs рекомендует меньше 500 строк на файл.

Влияют ли rules на Tab и автодополнение?

Нет. Project Rules и User Rules работают в Agent (чат). Cursor Tab и Inline Edit (Cmd/Ctrl+K) rules не используют – это зафиксировано в официальной документации Cursor.

User Rules или Project Rules – что выбрать?

Project Rules – в git, для всей команды и конкретного репозитория. User Rules – личные, только на вашем аккаунте, тоже только Agent. Не дублируйте одни и те же пункты в обоих местах – при конфликте Project Rules важнее для репозitorия, но дубли путают диагностику.

AGENTS.md или .mdc – что использовать?

AGENTS.md – простой markdown в корне без YAML, поддерживаются вложенные AGENTS.md в подпапках. Выбирайте .mdc, когда нужны alwaysApply, globs или разные режимы в одном проекте. Можно начать с AGENTS.md и перейти на .mdc при росте правил.
