Cursor Automations запускает Cloud Agent без вас: по расписанию, по ссылке webhook или при событии в GitHub. Ручной запуск в чате не масштабируется, когда нужен утренний digest, заявка с сайта или короткий review PR. За 30–45 минут вы соберёте первую automation на cursor.com/automations, выберете узкий триггер, проверите Run History и не упрётесь в billing или "пустой" webhook URL.

TL;DR / Быстрый инсайт: Automation = триггер + инструкция (prompt) + tools + scope репозитория. Cloud Agent в облачной "песочнице" выполняет задачу и пишет результат в Run History, Slack или PR. Cron в Automations считается в UTC; webhook URL и API key появляются только после Save. Перед первым run включите on-demand billing и оставьте ~$2 запаса до hard spending limit.

GA Automations – с 5 марта 2026: агенты в фоне с MCP и memory. Логика как в Make: узкий триггер, чёткий prompt, минимум tools. Ниже – cursor automations настройка: cron, webhook и GitHub PR.

1. Сравните Automations и ручной Cloud Agent

Cloud Agent – облачный ИИ-помощник Cursor (repo, PR, правки кода); запуск вручную из Agents. Automation – тот же агент по триггеру без вашего клика.

Scope репозитория задаёт, видит ли агент код:

Режим Когда выбирать Типичный триггер
Без репозитория Digest в Slack, разбор JSON с webhook без git Scheduled, Webhook
Один repo + ветка Review PR, push в main, cron с чтением кода GitHub PR, Scheduled
Multi-repo environment Несколько репозиториев в одном окружении агента Командные сценарии

Для триггеров GitHub, GitLab и push в ветку repo обязателен по документации Cursor. Для cron и webhook по умолчанию repo не нужен, пока вы не просите агента менять код. Ручной Cloud Agent удобен для разовых задач; automation – когда сценарий повторяется и его нужно стандартизировать для команды.

Делайте: одна automation – один узкий сценарий. Не делайте: вешать cron digest и тяжёлый event-trigger (Sentry, Linear) на одну запись – на форуме Cursor cron тогда может "залипать" как duplicate активного run.

2. Создайте automation на cursor.com/automations

Откройте cursor.com/automations → New Automation (или шаблон Marketplace, skill /automate).

Workflow первой automation:
Billing OK → New Automation → trigger → prompt → tools → repo scope → Save → test run → Run History
  1. Шаг 1: Paid-план с Cloud Agents; Automations нет на Start (India) – см. pricing.
  2. Шаг 2: В Integrations подключите GitHub или Slack, если выбранный триггер это требует.
  3. Шаг 3: Выберите один trigger: Scheduled, Webhook или GitHub pull request (не смешивайте на старте).
  4. Шаг 4: Напишите prompt: когда действовать, когда молчать, формат ответа; упомяните включённые tools (@-mention по UI).
  5. Шаг 5: Включите только нужные tools (Send to Slack, Comment on PR, MCP); лишние tools увеличивают стоимость run.
  6. Шаг 6: Задайте repo scope или оставьте "без repo" для чистого webhook/Slack.
  7. Шаг 7: Save & activate, затем manual Test run и проверка Run History.
  8. Шаг 8: Зафиксируйте имя automation и владельца в wiki команды.

Биллинг как у Cloud Agent, context window всегда на максимум модели. Делайте: короткий prompt со "stop". Не делайте: full review каждого PR.

3. Настройте cron-триггер с учётом UTC

Scheduled – "будильник" агента: пресеты или cron. Расписания считаются в UTC (форум Cursor); для MSK используйте перевод времени или CRON_TZ=Europe/Moscow. Cron с кодом – single repo и main.

Digest в 09:00 MSK: переведите в UTC с учётом offset или задайте CRON_TZ. Запуск может сдвинуться на минуты, но не раньше указанного слота (docs).

Forum bugs 2026: смена daily→weekly или зависший run ломают расписание. Делайте: удалить и пересоздать automation. Не делайте: править cron in-place при stale pattern в Run History.

4. Подключите webhook: Save, URL и Bearer key

Webhook – входящая "кнопка" по HTTP: форма, CI или Make шлёт POST, automation стартует. API (интерфейс запросов) здесь простой: один URL, один Bearer-key, JSON в теле. URL и key – только после Save automation (docs Cursor).

После Save – URL и API key; POST с Bearer, JSON в prompt (сверьте payload в Run History).

curl -X POST "https://YOUR_WEBHOOK_URL" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"lead":"test@example.com","source":"landing"}'

Если смените Run as с Me на Service account, docs требуют regenerate webhook API key и проверить MCP OAuth уже для service account. Сохраните key в password manager команды.

Делайте: один тестовый POST сразу после Save. Не делайте: светить key в Git или в клиентском JS – только backend.

5. Задайте сценарии GitHub PR, Slack и Linear

Триггер – это "если произошло X, запусти агента". Сравнение стартовых вариантов для cursor automations github pr и мессенджеров:

Триггер Repo Мини-шаблон prompt
GitHub PR opened Обязателен "Если diff < 200 строк – краткий review; иначе только checklist. Комментируй PR, не пушь."
Push to main Обязателен "Только high-risk изменения в auth/ – алерт в Slack; остальное игнорируй."
Slack message Часто без repo "Отвечай в тред только на @mention с keyword deploy."
Linear issue По сценарию "При смене статуса на Done – черновик release note в комментарий."

Fork PR не триггерят (docs); тест – PR внутри своего repo. MCP – гайд MCP; multi-repo – environment.json. Делайте: stop-условия. Не делайте: комментарий на каждый typo.

6. Пройдите чеклист billing, secrets и egress

Включите on-demand billing и spending limit; ~$2 headroom до hard cap (forum). Run as Me – на вас; Service account – team pool. Цены – models-and-pricing. Computer use по умолчанию включён.

  • Paid Cursor + Automations доступны на вашем плане
  • On-demand billing включён, spending limit задан
  • ~$2 запаса до hard limit (forum workaround)
  • Run as выбран осознанно (Me vs Service account)
  • После смены Run as – regenerate webhook key
  • MCP OAuth пройден для service account, если нужен MCP
  • Secrets только в настройках automation / env, не в prompt
  • Egress и домены MCP согласованы с политикой команды
  • Один узкий trigger на automation
  • Cron и event не смешаны на одной записи
  • Test run + Run History после каждого изменения
  • GitHub PR тест – не из fork
  • Run History: нет лишних skipped/duplicate без причины

Outbound webhooks статуса агента (HMAC X-Webhook-Signature) – отдельная настройка Cloud Agent API; не путайте с inbound webhook-триггером automation.

7. Запланируйте следующие шаги

  1. Доведите до зелёного статуса одну automation: cron, webhook или PR review.
  2. Три дня смотрите Run History: совпадает ли cron с ожидаемым UTC/MSK.
  3. Если нужны внешние сервисы – подключите MCP по инструкции.
  4. Вторую automation добавляйте только после стабильного первого run.
  5. Для install-скриптов и multi-repo сверьтесь с environment.json.

Частые вопросы

Нужен ли репозиторий для cron automation?

Нет для scheduled без кода: Slack-digest или разбор webhook JSON идут без repo. Да, если нужны коммиты или PR: выберите single repo, ветку и проверьте доступ GitHub в Integrations.

Как передать webhook body в prompt?

Сохраните automation, отправьте POST с JSON-телом и Bearer key, откройте Run History и убедитесь, что поля попали в контекст run. При необходимости явно опишите в prompt: "используй поля lead и source из тела запроса".

Почему cron automation запускается не по расписанию?

Проверьте UTC vs локальное время или CRON_TZ. Если расписание меняли – пересоздайте automation (известный баг stale scheduler). Убедитесь, что нет зависшего run и что cron не конкурирует с другим event на той же записи.

Почему не видно webhook URL?

Сначала нажмите Save automation – URL и API key генерируются только после сохранения. Затем скопируйте ключ в секретное хранилище и сделайте тестовый curl POST.

PR из fork не запускает automation – это баг?

Нет, это ограничение docs: fork pull requests не поддерживаются для PR-триггеров. Тестируйте на ветках внутри основного repo или используйте событие merged PR, если оно подходит под задачу.

На каком плане доступны Cursor Automations?

Нужен paid-план с Cloud Agents; Automations входят в продукт GA с марта 2026. Сверьте свой тариф в dashboard и в pricing – отдельные региональные планы могут отличаться.

Кто оплачивает run automation?

При Run as Me – usage на создателя; при Service account – на team usage pool. Задайте spending limit и запас до cap, иначе run может не начаться.
