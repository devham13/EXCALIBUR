Сотрудники ищут ответ в Confluence, а ChatGPT выдумывает регламент? RAG для базы знаний решает это: система сначала находит куски ваших PDF и wiki, потом формулирует ответ с цитатой. Ниже – полный workflow за 2–4 недели пилота: аудит 50–200 документов, chunking, hybrid search с rerank, промпт без галлюцинаций, eval на 20–30 вопросах и канал с эскалацией к человеку. После гайда вы соберёте рабочий прототип rag системы на корпоративных файлах без команды из пяти разработчиков.

TL;DR / Быстрый инсайт: RAG (Retrieval-Augmented Generation) – это "ответ по вашим документам": поиск релевантных фрагментов + генерация текста языковой моделью. Пилот: один сценарий (поддержка, HR или продукт), 50–200 актуальных файлов, hybrid BM25 + vector, rerank top-20 до top-3–5, temperature 0 и golden dataset из 20–30 вопросов. По данным Novacom, около 70% качества RAG определяет retrieval, не модель. Запрос "rag база знаний" – около 419 показов/мес в Вордстате (июнь 2026, вторичные данные).

RAG для базы знаний – конвейер: документы режутся на чанки, превращаются в embeddings (числовые "отпечатки" смысла) и лежат в vector store. По запросу система достаёт 3–5 фрагментов и просит LLM (языковую модель) собрать ответ. Без retrieval модель фантазирует; с плохим chunking – находит не то. Для пилота держите один отдел, не "вся компания сразу".

Схема RAG-pipeline:
Документы → парсинг/OCR → chunking + метаданные → embed → vector DB (+ BM25)
Запрос → ACL-фильтр → hybrid search → RRF → rerank top-20→5 → промпт + LLM → ответ + citations
Re-index (cron/webhook) ← owner базы + eval golden dataset каждый спринт

1. Проведите аудит документов и разметьте права доступа

Начните с одного сценария: FAQ поддержки, онбординг HR или продуктовая wiki. Соберите 50–200 актуальных файлов из Confluence, Notion или Google Drive – не архив за пять лет. Назначьте owner базы: человек, который решает, что индексировать и когда перезапускать.

ACL (список "кто что видит") проверяйте до поиска и до LLM, не только в промпте. Метаданные: file_name, section, updated_at, acl. Удалите дубликаты – иначе бот цитирует старый регламент.

Делайте: whitelist источников на пилот. Не делайте: индексировать сканы PDF без OCR – Managed-сервисы часто их не читают.

2. Настройте chunking, embeddings и ingestion

Режьте по заголовкам, не посередине абзаца. Старт: 256–512 или 500–700 токенов, overlap 10–20%. Сканы PDF – только через OCR.

Embedding-модель зафиксируйте до индексации – смена = полный re-index. PoC: BGE-M3 или text-embedding-3-small; для 152-ФЗ – YandexGPT/GigaChat + on-prem. Re-index через cron в n8n/Make; храните hash файла.

Делайте: логируйте, какой chunk попал в ответ. Не делайте: менять chunk_size каждый день без eval – не поймёте, что улучшилось.

3. Включите hybrid search и reranking

Vector-only промахивается по артикулам и номерам договоров. Hybrid: BM25 (поиск по словам) + vector (по смыслу) → RRF (слияние списков по рангам, k≈60) → rerank top-20 до top-3–5. Reranking даёт +10–25% к retrieval (Novacom). ACL-фильтр в query обязателен.

Делайте: порог similarity для отсечения шума. Не делайте: скармливать LLM 20 чанков – эффект Lost in the Middle: точность падает, если ключевой факт в середине длинного контекста (Liu et al., TACL 2024).

4. Напишите промпт RAG с цитатами и честным "нет в базе"

System prompt – главный руль. Шаблон:

Отвечай только по контексту ниже. Если данных нет – скажи "В базе нет информации" и предложи эскалацию.
Цитируй источник: [file_name, section].
Не выдумывай цифры, сроки и юридические формулировки.

Temperature 0 – минимум фантазии. Логируйте fallback "не нашёл". Юридические и HR темы – только эскалация к человеку.

Делайте: показывать пользователю ссылку на исходный документ. Не делайте: просить модель "ответить красиво", если контекст пуст.

5. Организуйте eval, re-index и мониторинг

Golden dataset: 20–30 реальных вопросов сотрудников на пилоте, 50–100 на prod. Для каждого – эталонный ответ и ссылка на источник. Метрики RAGAS: faithfulness (ответ не противоречит контексту) и context precision (найденное – по делу). Re-index: webhook при сохранении в Confluence или cron раз в ночь. Чеклист перед prod:

  1. Один сценарий и owner базы зафиксированы
  2. 50–200 актуальных документов, дубликаты удалены
  3. ACL в query, не только в промпте
  4. Chunk size проверен на golden dataset
  5. Embedding-модель зафиксирована, hash файлов в метаданных
  6. Hybrid + rerank включены, top-3–5 в промпт
  7. System prompt с "нет в базе" и citations
  8. Temperature 0, логи fallback
  9. Golden dataset 20+ вопросов, baseline RAGAS записан
  10. Re-index по webhook/cron настроен
  11. Канал (Telegram/виджет) с 👍/👎 и эскалацией
  12. Юридические темы – только human-in-the-loop

Делайте: сравнивать eval до/после каждого релиза индекса. Не делайте: выкатывать на весь штат без недели внутреннего beta.

6. Сравните стек: Chroma, Qdrant, pgvector, Dify

Критерий ChromaDB (PoC) Qdrant pgvector Dify
Старт pip, zero config Docker / cloud Ext. PostgreSQL SaaS или self-host UI
Hybrid + rerank Вручную / LangChain Native sparse+dense+RRF SQL BM25 + vector Pipeline в интерфейсе
ACL Фильтры в приложении Payload filters Row-level + WHERE Роли workspace
152-ФЗ / on-prem Self-host Self-host Yandex Managed PG Self-host edition
Когда выбрать Пилот до ~1k docs Prod, hybrid native Уже есть PostgreSQL MVP без Python за дни
Итоговый вердикт: PoC за выходные – Chroma + LangChain; prod – Qdrant или pgvector + n8n cron для re-index. Dify – если команда без DevOps и нужен UI. Managed RAG облака ускоряют старт, но проверьте лимиты (PDF без OCR, max 25 МБ на файл у Cloud.ru) и vendor-lock.

Делайте: выбирайте стек под eval, не под хайп. Не делайте: переносить PoC на prod без смены vector DB и ACL-слоя.

7. Пройдите восемь шагов пилота за 2–4 недели

  1. Шаг 1: Сценарий. Выберите FAQ поддержки, HR или продукт; соберите 50–200 файлов; назначьте owner; разметьте ACL.
  2. Шаг 2: Корпус. Парсинг, dedup, chunking 256–512 или 500–700 tok, overlap 10–20%, метаданные file_name, section, updated_at, acl.
  3. Шаг 3: Стек PoC. Chroma или Qdrant + embedding; зафиксируйте модель; для 152-ФЗ – on-prem и российская LLM.
  4. Шаг 4: Ingestion. Embed в vector store; cron/webhook re-index; hash и версия индекса.
  5. Шаг 5: Retrieval. Hybrid vector + BM25 → RRF k≈60 → rerank top-20 → top-3–5; ACL в query.
  6. Шаг 6: Промпт. "Только контекст", citations, temperature 0, лог "нет в базе".
  7. Шаг 7: Eval. Golden dataset 20–30 вопросов; RAGAS faithfulness и context precision после каждого изменения.
  8. Шаг 8: Канал. Telegram/виджет/Slack; 👍/👎; эскалация на юридические темы; мониторинг latency.

Публичную базу на сайте – по гайду GEO-оптимизация 2026. Re-index в Make – на курсе kv-ai.ru.

8. Что делать дальше

  1. Зафиксируйте baseline eval до любых правок chunking.
  2. Подключите один канал (Telegram или виджет) только для пилотной группы.
  3. Раз в спринт прогоняйте golden dataset и сравнивайте с прошлым sprint.
  4. После стабильного faithfulness масштабируйте источники – не наоборот.
  5. Если нужен UI без кода – протестируйте Dify параллельно с Chroma PoC.

Частые вопросы

Сколько документов нужно для первого RAG?

50–200 актуальных файлов на один сценарий – не вся компания. Лучше узкий FAQ поддержки, чем 10 000 страниц без owner.

Чем hybrid search лучше vector-only?

BM25 ловит артикулы и номера договоров; vector – синонимы и перефраз. RRF объединяет оба списка без сравнения "несопоставимых" score. На корпоративных формулировках прирост порядка 5–10% к точности (May AI, июнь 2026).

Как обновлять базу без потери качества?

Re-index по webhook или cron при изменении файла; храните hash и версию индекса; после каждого re-index прогоняйте golden dataset – если faithfulness упал, откатите chunk или top-k.

Какой размер чанка для русского регламента?

Старт 256–512 или 500–700 токенов с overlap 10–20%. Проверьте на своих 20–30 вопросах – универсальной цифры нет.

Нужен ли reranker?

Да, если baseline промахивается по точным формулировкам. Схема top-20 → rerank → top-3–5 в LLM; прирост качества retrieval 10–25% по Novacom.

Как не допустить утечки закрытых документов?

ACL-фильтр в query vector DB до генерации – права проверяются до поиска и до передачи текста в LLM, не только в system prompt.

RAG или fine-tuning?

RAG – для меняющихся регламентов и FAQ: обновили PDF – re-index. Fine-tuning – для стиля ответа или формата, когда факты стабильны.
