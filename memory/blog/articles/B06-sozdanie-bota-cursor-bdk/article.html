Хотите агента, который просыпается от pull request в GitHub, проходит регрессионные тесты и живёт в Git, а не в одной форме в dashboard? Cursor BDK (Bot Development Kit) – это как рецепт и ингредиенты в репозитории: Markdown-инструкции, TypeScript-tools, evals и деплой на Cursor-managed hosting. За одну сессию вы пройдёте init → bdk dev → smoke-eval → GitHub fixture → push и bdk deploy с service account и поймёте, когда хватит Cursor Automations.

TL;DR / Быстрый инсайт: BDK – open-source движок тех же ботов, что Security Review и Rollouts: проект в Git с папками bot/ и evals/. Старт: Node 22.13+, npx @cursor/bdk init, bdk dev. Качество: evals/**/*.eval.ts и bdk eval. GitHub без prod-webhook: bdk github replay → fixtures. Деплой только с запушенного ref и CURSOR_SERVICE_ACCOUNT_KEY после bdk validate. Automations – prompt+trigger в UI; BDK – когда нужны версии, тесты и свой код.

Bot Development Kit cursor – не Telegram-бот в IDE и не Grok в приложении. Это npm-пакет @cursor/bdk (линия около 0.2.18 на jsDelivr): bdk init, bdk dev, bdk eval, bdk deploy. MCP (Model Context Protocol) для tools – см. подключение MCP в Cursor.

1. Сравните BDK, Cursor Automations и Grok Bot: таблица выбора

Три формата решают похожие задачи, но по-разному хранят логику. API (Application Programming Interface) в BDK – это ваши tools и channels в коде, а не только чат.

Критерий Cursor BDK Cursor Automations Grok Bot
Где живёт логика Репозиторий: TS + Markdown Prompt и trigger в dashboard Интерактив в приложении Cursor
Тесты и версии evals/, Git, CI с bdk eval --json Без полноценного eval-проекта в Git Не ваш self-serve репозиторий
Триггеры GitHub, Slack, webhooks, schedules GitHub, GitLab, Slack, Linear, webhooks Чат с пользователем
Деплой Cursor-managed hosting или свой процесс Облако Cursor без вашего bot/ Не применимо
Когда брать PR-бот, triage, кастомные tools/MCP Повторяющийся job без кода в Git Быстрый диалог, не production-агент
Итоговый вердикт: Если нужен только cron + prompt на репозиторий – начните с Automations. Если нужны hillclimb, fixtures и bdk deploy – берите BDK.

Делайте: зафиксируйте выбор в README репозитория. Не делайте: смешивать Automations и BDK в одной инструкции для команды – разные циклы обновления.

2. Проверьте требования и создайте проект через bdk init

Минимум Node 22.13+ (проверка node -v), Git и аккаунт Cursor. Bun для BDK не подходит: на встроенных tools часто NGHTTP2_FRAME_SIZE_ERROR – используйте только Node.

Маршрут за сессию:
node -v → bdk init → правка bot/instructions.md → bdk dev → evals/smoke.eval.ts → bdk github replay (fixtures) → git push → bdk validate → bdk deploy → status running

Scaffold без глобальной установки:

npx @cursor/bdk init ./my-agent
cd my-agent
bdk dev

Шаблоны init: security-reviewer, grokbot-agents, triage-linear, triage-jira (--template triage → linear). Документация: bdk docs; при bdk serve – также /docs.

Дерево после init (упрощённо):

my-agent/
  bot/
    instructions.md
    tools/
    mcp-connections/
    channels/
  evals/
    (ваши *.eval.ts здесь, не в bot/evals/)

Делайте: открыть папку в Cursor и читать bot/instructions.md первым. Не делайте: класть eval-файлы в bot/evals/ – CLI их игнорирует; только evals/**/*.eval.ts.

  1. Шаг 1: Убедитесь, что node -v показывает 22.13 или выше; при необходимости обновите через nvm или fnm.
  2. Шаг 2: Выберите шаблон: пустой init или --template security-reviewer для PR-ревью.
  3. Шаг 3: Выполните npx @cursor/bdk init ./my-agent и зайдите в каталог проекта.
  4. Шаг 4: Запустите bdk dev и дождитесь локального playground.
  5. Шаг 5: Сохраните slug проекта и структуру bot/ в README для команды.

3. Настройте bot/instructions.md, tools, MCP и subagents

instructions.md – "должностная инструкция" агента: тон, границы, когда звать tools. Tool – функция в bot/tools/, которую модель может вызвать по имени. MCP – внешние серверы через bot/mcp-connections/ (как "розетки" к GitHub, браузеру, docs); для IDE-сервера см. наш гайд по MCP в Cursor, для BDK – defineConnection в mcp-connections с advertiseTools: true при отладке.

Для GitHub добавьте channel bot/channels/github.ts с githubChannel(): prod использует cursorAccount и serve --cursor-events; локально – unsigned loopback и fixtures.

Делайте: один channel и 2–3 tools на первый smoke. Не делайте: печатать CURSOR_SERVICE_ACCOUNT_KEY или webhook secret в instructions.md – только env и секреты CI.

4. Прогоните локально bdk dev, bdk run и первые evals

Локальный цикл: bdk dev → playground → bdk run --message "..." или bdk call для детерминированного tool без полного диалога.

Eval – автоматический сценарий "агент должен сделать X". Файл evals/smoke.eval.ts с defineEval, gate t.succeeded() и calledTool на нужный tool. Запуск:

bdk eval --dir . --list
bdk eval --dir . --tag smoke

Model turns в evals требуют credential Cursor: bdk login, API key или service account в env. Hillclimb: измерили → одна правка (lever) → снова bdk eval; каждое улучшение фиксируйте eval, иначе регрессия незаметна.

Делайте: в CI добавьте bdk eval --json --no-stream --junit reports/evals.xml. Не делайте: запускать eval под Bun – только Node 22.13+.

5. Подключите GitHub channel и задеплойте на Cursor-managed hosting

Prod webhook не обязателен для первой отладки. Синтез payload:

bdk github replay owner/repo#123 --dir . --dry-run --out fixtures/github

Затем в режиме --dev отправьте fixture curl-ом с заголовком x-github-event. Replay по умолчанию тянет pull_request; для других событий уточните --events в CLI.

Деплой берёт только запушенный Git ref – незакоммиченные файлы на hosting не попадут.

  1. Шаг 1: git add, commit, push; проверьте git branch -r --contains HEAD.
  2. Шаг 2: export CURSOR_SERVICE_ACCOUNT_KEY (значение из dashboard, не коммитьте).
  3. Шаг 3: bdk validate --dir . и исправьте ошибки до deploy.
  4. Шаг 4: bdk deploy --dir . --ref HEAD (или явный tag/sha).
  5. Шаг 5: Дождитесь status running, не pending/deploying; сохраните slug и флаги --cursor-events-repo / --allow-domain при redeploy.

Делайте: service account для CI отдельно от личного bdk login. Не делайте: deploy до зелёного smoke-eval.

6. Устраните типичные сбои CLI, login и pending deploy

  • Eval падает на API key – задайте credential для model turns (service account или bdk login)
  • NGHTTP2_FRAME_SIZE_ERROR – вы на Bun; переключитесь на Node
  • MCP tools не видны – advertiseTools: true и проверьте OAuth MCP по skill bdk-mcp-auth
  • Deploy завис в pending – дождитесь running или смотрите validate/deploy логи
  • GitHub replay пустой – проверьте gh auth и номер PR
  • evals не находятся – путь evals/**/*.eval.ts, не bot/evals/
  • Локальные правки не на prod – нужен push, deploy не заливает рабочую копию
  • Redeploy сбросил events – сохраните те же --cursor-events-repo и --allow-domain
  • Нет Node 22.13 – bdk init/dev могут вести себя непредсказуемо
  • Путаете @cursor/july и @cursor/bdk – в user-facing тексте и npm используйте @cursor/bdk
  • Ждёте Telegram-гайд – это другой продукт; BDK только через init/eval/deploy

Делайте: bdk docs и skills на jsDelivr при расхождении с памятью. Не делайте: выдумывать Teams/Enterprise pricing для self-serve BDK-проекта.

7. Что делать дальше

  1. Добавьте второй eval на GitHub fixture после replay.
  2. Подключите MCP tool под ваш стек по гайду MCP.
  3. Включите bdk eval в GitHub Actions на каждый push.
  4. Документируйте slug и ref деплоя в README.
  5. Если агент дополняет сценарии Make – разберите связку на курсе Make.com и вайбкодинга (фоновые цепочки после BDK).

Частые вопросы

Чем BDK отличается от Cursor Automations?

Automations: prompt и trigger в dashboard, без полного TS/MD проекта в Git. BDK: версионируемый репозиторий, evals, custom tools, MCP и выбор hosting. Выберите Automations для простого job; BDK – когда нужны тесты и код channel.

Нужен ли отдельный репозиторий для деплоя BDK?

Нужен Git remote с запушенным ref. bdk deploy читает коммит на сервере, а не ваши незакоммиченные файлы. Перед deploy выполните push и git branch -r --contains HEAD.

Как писать evals для BDK агента?

Создайте evals/**/*.eval.ts с defineEval; проверяйте t.succeeded(), calledTool / notCalledTool. Для GitHub сгенерируйте fixtures: bdk github replay … --dry-run --out fixtures/github и прогоните eval на fixture в --dev.

Можно ли тестировать GitHub без admin webhook?

Да. Используйте bdk github replay и каталог fixtures; локально POST на dev-сервер с x-github-event. Prod webhook и cursorAccount настраиваются отдельно при serve --cursor-events.

Что нужно для bdk deploy?

CURSOR_SERVICE_ACCOUNT_KEY в env, успешный bdk validate, push в remote, затем bdk deploy --dir . --ref. В CI используйте service account, не личный login разработчика.

Почему eval падает с ошибкой API key?

Ходы модели в evals требуют Cursor credential. Локально: bdk login или ключ в env. В CI: service account в секретах репозитория. Без credential eval не пройдёт model turns.

Node или Bun для BDK?

Только Node 22.13+. Под Bun типичны сбои HTTP/2 на tools. Проверьте which node и node -v перед bdk dev и bdk eval.
